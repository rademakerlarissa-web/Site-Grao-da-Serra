Bastidores

A ideia central

Vários sistemas usam o mesmo banco: o aplicativo do balcão, o caixa e os relatórios da gerência. Por isso as regras do negócio ficam no próprio banco. Qualquer sistema que se conecte segue as mesmas regras, sem precisar reprogramá-las. O objetivo do exercício é perceber em que situação cada recurso é a escolha mais adequada.

Function

Calcula e devolve um valor

O que é
Recebe parâmetros, faz um cálculo e devolve um único valor. Pode ser usada dentro de um SELECT, de uma view, de uma procedure ou de um trigger.
Use quando
A mesma conta ou regra aparece em vários lugares. Escrita uma vez, todos chegam ao mesmo resultado. Se a regra mudar, muda em um ponto só.
No projeto
fn_total_pedido, fn_situacao_estoque, fn_desconto_fidelidade.
Em uma frase
Calcula uma vez, e todo mundo chega ao mesmo resultado.
Procedure

Executa uma operação do negócio

O que é
Agrupa vários comandos em uma operação, chamada com CALL.
Use quando
A operação altera dados e precisa de validação. Quem chama só informa os parâmetros, e o banco garante todos os passos, sempre na mesma ordem. Quando algo não pode ser feito, a procedure para com SIGNAL e uma mensagem em português.
No projeto
sp_abrir_pedido, sp_adicionar_item, sp_finalizar_pedido, sp_reajustar_precos_categoria.
Em uma frase
O banco garante os passos, e a tela só pede.
View

Entrega os dados prontos

O que é
Uma consulta salva com um nome, usada como se fosse uma tabela.
Use quando
Cada sistema ou perfil precisa de exatamente os dados que lhe cabem. Quem consulta não precisa conhecer os JOINs nem enxerga colunas que não deveria ver.
No projeto
vw_cardapio, vw_pedidos_detalhados, vw_produtos_para_repor, vw_vendas_por_categoria.
Em uma frase
A tela faz um SELECT simples, e o JOIN fica escondido na view.
Trigger

Acontece sozinho

O que é
Um bloco que o banco executa antes (BEFORE) ou depois (AFTER) de um INSERT, UPDATE ou DELETE em uma tabela.
Use quando
Algo precisa acontecer sempre, sem depender de alguém lembrar: manter dados consistentes, registrar auditoria e bloquear alterações indevidas, venha o comando de onde vier.
No projeto
trg_item_baixa_estoque, trg_item_devolve_estoque, trg_produto_historico_preco, trg_pedido_bloqueia_alteracao. NEW vale no INSERT e OLD no DELETE. O bloqueio é BEFORE porque age antes de gravar.
Em uma frase
Acontece sozinho, até para quem mexe direto no Workbench.

    Arquitetura da conexão

    O navegador não acessa o MySQL diretamente. Nesta aplicação, o JavaScript da página envia requisições HTTP para uma API local em Node.js e Express. Quando o MySQL está disponível, o servidor usa mysql2 para consultar o banco grao_da_serra e devolve os resultados em JSON. Se o banco estiver indisponível, a tela usa dados fictícios e simula as operações apenas nesta sessão; nada é gravado no MySQL. As credenciais ficam no arquivo local .env, que não é servido ao navegador nem versionado.

    Caminho de uma operação

    • 1.Interface: app.js chama uma função assíncrona de dados.js.
    • 2.API: dados.js usa fetch; server.js valida a requisição e executa SQL com parâmetros.
    • 3.MySQL: views e procedures existentes fornecem os dados e aplicam as regras; triggers cuidam dos efeitos relacionados.
    • 4.Resposta: a API devolve JSON. Erros SIGNAL das procedures são enviados à faixa de avisos.

    Configuração e execução local

    1. Execute 01_base_grao_da_serra.sql uma vez para criar as tabelas e os dados iniciais. Depois execute 02_questoes_1_a_15_referencia.sql para criar as functions, procedures, triggers e views. O segundo script recria esses objetos; não apaga as tabelas nem os dados.

    2. Instale Node.js e inicie o MySQL. Crie um usuário do banco para a aplicação com as permissões necessárias; evite usar o usuário administrador no uso diário.

    3. Na pasta do projeto, instale as dependências com npm install. Para usar o MySQL, copie .env.example para .env e preencha host, porta, banco, usuário e senha. Sem essa configuração, ou se o banco estiver indisponível, a página inicia com dados fictícios. O .env é local e está excluído do Git.

    4. Execute npm start e abra http://127.0.0.1:3000. A verificação da API fica em /api/health.

    Se o MySQL estiver em outra porta, ajuste DB_PORT no .env. Não abra index.html diretamente como arquivo: use o endereço servido pelo Node.js.

    Usuário MySQL da aplicação

    Se ainda não tiver um usuário próprio, entre no Workbench com uma conta administradora e execute o exemplo abaixo. Troque a senha de exemplo e use a mesma no .env. Se já existe um usuário para a aplicação, configure as credenciais dele em vez de criar outro.

    CREATE USER IF NOT EXISTS 'grao_app'@'127.0.0.1' IDENTIFIED BY 'TROQUE_ESTA_SENHA';
GRANT SELECT ON grao_da_serra.* TO 'grao_app'@'127.0.0.1';
GRANT DELETE ON grao_da_serra.item_pedido TO 'grao_app'@'127.0.0.1';
GRANT EXECUTE ON grao_da_serra.* TO 'grao_app'@'127.0.0.1';

    Resumo da implementação

    A interface HTML/CSS/JavaScript chama funções assíncronas em dados.js. Essas funções usam fetch para acessar uma API Node.js/Express em server.js. O servidor usa mysql2 e as credenciais do .env para consultar o banco grao_da_serra; os dados voltam em JSON. Consultas de leitura usam as views do banco, e operações de pedido e reajuste chamam as procedures. O banco permanece responsável pelas regras e pelos triggers de estoque e auditoria.
